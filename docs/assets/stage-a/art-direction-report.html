01 / Executive visual assessment

The live social core is credible. Real authors, immutable parent attribution, field changes, comments, Agree state and conservative reputation accounting already work together. The main weakness is explanation through hierarchy: a visitor can read a trading post before understanding what makes FORK different.

  1. The signature is underexposed. Tree links sit in secondary rails and, on mobile detail, below much of the conversation. The two-node Tree occupies a large canvas but does not display the numerical differences that make the fork meaningful.
  2. Typography is inconsistent with its declared intent. CSS names Geist/Inter but the root layout does not load them. A live computed body chain showed Apple/system/Roboto/Helvetica Neue/Nanum Gothic instead. Stage B must identify and control the overriding rule, not merely change font names. Multiple 9–11px labels weaken the premium impression and readability.
  3. Empty space often carries filler instead of context. Repeated sidebar manifestos, large profile covers and four discovery cards consume attention while only two actual ideas exist. Do not manufacture more content. Make the genuine journey legible.
  4. Semantic color is overloaded. Green marks navigation, root cards, selection, Long and a dot beside “Not executed.” Anchored provenance, bullish direction, selection and execution must have distinct meanings.
  5. The presentation is behind the implementation. README still opens as a build specification and discusses execution/Nansen ambitions before the proven live product. This is a submission risk, not just a copy issue.

Keep: dark restraint, the branch mark, social-first navigation, the Fork verb, visible author attribution, existing real data/API/security boundaries, field-diff logic, the Emerging sample threshold, tabular numbers, focus styles and reduced-motion support. Polish their presentation before adding features.

Method: read-only production browser audit plus repository source review. Nine settled views × 1440/1280/390px; additional initial-render, empty and missing-thesis evidence. No publish, fork, reaction, comment, wallet signature or blockchain transaction was submitted. Visual responsive testing is browser viewport resizing, not certification on physical iOS/Android devices. Reference accessibility/performance comments are design observations; no Lighthouse or complete WCAG audit was run.

07 / Signature Idea Tree redesign plan

The first view should answer: whose idea was first, who contributed, and what changed. Today the selected Tree node routes to another Tree URL; this can reload/reframe the canvas. Long reasoning paragraphs occupy node space while real numeric differences are absent.

  1. Two-node desktop: fit the genuine #1 → #2 pair to a compact central lineage region, not an oversized empty graph. Root at the left, child at the right; each node 264–288px with ID, author, ETH/Long and concise parameter row. One connector names “Target + leverage”; a detail pane carries full reasoning and old/new values.
  2. Selection: click/Enter selects locally, announces “Fork #2, by …, from #1,” updates a stable detail pane and retains graph position. Separate “Open thesis” link preserves real /t/2 navigation; optional URL replacement uses existing /t/2/tree only after history behavior is tested. No API contract change is necessary.
  3. Diff: target $4,200 → $4,400; leverage 2× → 3×; invalidation $3,600 unchanged. Reasoning has changed too: show two labeled excerpts or a disclosed comparison. Numeric increases do not mean an objectively better or profitable idea.
  4. Progressive disclosure: node preview is concise; a visible affordance opens reasoning and provenance. Hover only supplements click/focus. Root, parent, selected node and ancestor path use geometry/labels as well as color.
  5. Mobile: native-width vertical root → child timeline, no tiny panned canvas. Put numerical diffs between nodes; selected details follow in normal flow. Keep author links and Fork/Open thesis controls reachable without hover.
  6. Larger trees: preserve existing server cap/truncated-tree messaging and selected ancestry. Show immediate ancestors/children first; collapse other branches. Memoize child lookup and selection. Add explicit “Show branches” rather than rendering 250 dense text nodes. Use synthetic large-tree tests only in the test environment; never invent activity in the public graph.

React Flow decision: do not add it for P0. Existing tree data and read-only DOM/CSS connectors already work. Redesign node hierarchy and selection first, using small SVG paths if necessary. A framework introduces viewport/layout/accessibility/state work that does not solve missing diffs. Reconsider P1/P2 only when real branch density requires pan/zoom, fit-to-view and spatial navigation. If adopted: lazy-load only the Tree route, immutable node identities, memoized components/handlers, narrow subscriptions, collapsed branches and a keyboard/list fallback. These constraints follow React Flow’s performance guidance and accessibility documentation.

11 / Purposeful motion plan

With reduced motion, all nodes/connectors/diffs appear immediately. Native links and the full proposition remain useful with JavaScript unavailable.
